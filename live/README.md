# Live forward test

This folder holds the only test of the headline claim that cannot be affected by choices made after seeing results. Forecasts are written once, hashed, listed in a manifest and committed. They are scored later, when the volatility they predict has been realised.

## What is forecast

For Brent and WTI, the annualised realised volatility over the next 5, 22 and 66 trading days, from six models:

| Model | Meaning |
|---|---|
| `naive` | volatility of the last 22 days |
| `har_bc` | HAR on log volatility (5, 22, 63 days), variance-corrected for QLIKE |
| `lhar_bc` | HAR with leverage terms, variance-corrected |
| `lhar_ovx_bc_lag1` | the headline: leverage HAR with OVX of the previous trading day, variance-corrected |
| `garch_t` | GARCH(1,1) with t errors |
| `gjr_t` | GJR-GARCH(1,1) with t errors |

The procedure is the backtest procedure applied to the last row of the data: the models are fit on all origins whose targets are already realised, then predict the latest origin. Code: `src/oilfc/live/forecast.py`.

## Files

- `forecasts/{asset}_{origin}.json`: one frozen forecast. It holds the content, the run time (UTC), the code version (git commit, with `+dirty` if the code had uncommitted edits) and a SHA-256 of the content.
- `forecasts/MANIFEST.csv`: one row per forecast with the same hash.
- `scores.csv` and `SUMMARY.md`: generated by `experiments/live_score.py` (never edited by hand).

A forecast file is never overwritten: a second run for the same origin leaves the first one untouched.

## How to run

```bash
.venv/Scripts/python.exe experiments/live_run.py     # refresh data, write new forecasts
git add live/forecasts && git commit -m "chore(live): forecasts for <origin>"
.venv/Scripts/python.exe experiments/live_score.py   # verify hashes, score finished windows
```

The same steps run by hand when needed (EIA prices arrive about once a week). Commit the forecast files straight away: the commit time is the evidence that the forecast was fixed before its target window ended. Pushing the repository to GitHub adds a second, outside time stamp.

## Automation

From 2026-11-24 a GitHub Actions workflow (`.github/workflows/live.yml`) does the routine above every day at 20:00 UTC. It refreshes the data, writes forecasts for any new origin, verifies every stored hash, scores finished windows and pushes the new files to `main` as `github-actions[bot]`. Most days nothing is new and nothing is committed, because EIA publishes spot prices about once a week.

- **The outside time stamp** is the commit time on GitHub, set by GitHub and not by this computer.
- **Stopping it:** Actions tab, "Live forecasts", the three dots, "Disable workflow". Run it by hand with "Run workflow".
- **Pull before you push.** The bot adds commits to `main`, so run `git pull --rebase` before pushing your own work.
- **Failures** turn the run red and GitHub emails the repository owner. A hash mismatch also fails the run before anything is pushed.
- **GitHub switches off scheduled workflows after 60 days without repository activity.** Check the Actions tab now and then.
- **Platform.** The first two forecasts (origin 2026-11-17) were written on Windows by hand, later ones on Ubuntu by the workflow. Numerical differences between the platforms are far below the precision that matters (about 1e-6 in volatility).

## What this test does and does not show

- **Information timing.** A forecast at origin t uses prices through t and OVX through t-1. EIA publishes spot prices about a week late, so the run date is later than the origin and the first days of the target window may already have happened when the forecast is written. The code never sees them, but the time stamp only proves the forecast was fixed before the later part of the window.
- **Missed origins are not filled in afterwards.** Each run forecasts the latest origin only. Origins that were skipped stay skipped, which does not bias the result because the run schedule does not depend on outcomes.
- **Overlap and sample size.** Windows of 5, 22 and 66 days overlap, and there are few origins at first. `experiments/live_score.py` reports mean QLIKE and the gain over naive, but a significance test is not meaningful before roughly 60 origins per horizon. The planned test is Diebold-Mariano with the Harvey correction, as in the backtest.
- **Data after 2025-07-01.** The development rule that the holdout is never evaluated applies to the research experiments. Live forecasts use all data up to the origin, because that is what a real forecaster has.
- **What counts as success (proposed, fixed here before any live window is scored, for Aayush to confirm).** The headline model should have a lower mean QLIKE than `naive`, `har_bc`, `lhar_bc`, `garch_t` and `gjr_t` at 5 and 22 days on both assets, with Diebold-Mariano p below 0.05 after enough origins. A result against this is reported as it comes.
